# Ensemble Blender Tool — NOAA GEFS · ECMWF IFS ENS · ECMWF AIFS ENS · Canadian GEPS · NOAA AIGEFS · Blends

A static, GitHub-Pages-hosted web map of **ensemble mean sea-level pressure (MSLP), 10 m wind speed and 10 m wind gust (mph)** from five ensemble systems — **NOAA GEFS (31 members)**, **ECMWF IFS ENS (51 members)**, **ECMWF AIFS ENS (51 members, AI-based)**, the **Canadian GEPS (21 members)** and **NOAA AIGEFS (31 members, AI-based)** — viewable **per system or as a blend of any two or more**, rebuilt automatically every model cycle by a GitHub Action.

The toolbar tabs use the short names GEFS / IFS / AIFS / GEPS / AIGEFS (hover for the full name). Switch with the *Ensemble* toolbar buttons / menu, or keys **G**, **E** (IFS), **I** (AIFS), **C**, **A**, **B**. ## 1. Run it locally

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
python -m pytest -q                                     # 26 tests, no network needed

# quick smoke test: 6 members, first 24 h (≈ 65 requests, ≈ 16 MB)
python -m gefs_pipeline build --out dist --max-fh 24 --members 6        # --families gefs  (or ifs) to build one system only

# full production build: GEFS 31 + IFS 51 + AIFS 51 + GEPS 21 + AIGEFS 31 members, f000-f240 = 10 days (pressure only: ≈ 8 000 requests; **with 10 m wind and gust ≈ 20 000 requests and roughly 13 GB; a real build of all four available systems took 53 minutes with the Google mirror at 5 requests/s (limited by that ceiling, not by errors: 0 retries), so the default ceiling is now 12** – the ECMWF bucket's gentler cap of 3 requests/s, shared by IFS ENS and AIFS ENS, is the bottleneck: ≈ 14 700 requests ÷ 3 per second ≈ 80 min, while the other systems download alongside it – add `--no-wind` to skip them; the figures are extrapolated from measured small builds, the first full run will tell; the published site is ~18 MB without and roughly 50–60 MB with wind, see *Browser-side processing* and *10 m wind and gust*)
python -m gefs_pipeline build --out dist

python -m http.server 8000 --directory dist             # open http://localhost:8000
```

Useful flags: `--cycle 2026111806` (pin a run), `--max-fh`, `--members N`, `--rps 4` (slow down), `--workers`, `--no-cache`, `-v`.
`python -m gefs_pipeline resolve-cycle` just prints the newest complete cycle.

## 2. What the pipeline does

1. **Pick the cycle.** Starting at the current time, step back through the cycles in `[run] cycles` (default **00Z and 12Z** – the ECMWF runs that reach day 15) until one is *complete for every family* (GEFS: last forecast hour exists for all 31 members; ECMWF IFS ENS: last step of the ensemble and control streams is published; GEPS: the first and last all-member files exist; AIFS ENS and AIGEFS are *optional*, see below), so a half-published run is never shown and both systems always share the same initialisation time. Add 06/18Z to `cycles` for a GEFS-led site; ECMWF then ends at F144 for those cycles (the viewer shows exactly the hours each system has).
2. **Pick the grid per forecast hour – highest resolution first.**
   `pgrb2sp25` (**0.25°**) is probed first; if the object does not exist, `pgrb2ap5` (0.5°) is used.
   Verified against the bucket: **0.25° exists for f000–f240, exactly the 10-day window this project is configured for (`[forecast] stop = 240`)**, so every frame is 0.25°. The 0.5° product is only a safety net if a 0.25° object is missing; it can also serve longer runs (raise `stop` up to 384: f246+ exist only at 0.5° and are cubic-spline-upsampled for contouring). The viewer labels every frame with its grid.
3. **Download only the MSLP bytes (HTTP Range).**
   For each member × hour the client reads the tiny `.idx` inventory, finds the `PRMSL:mean sea level` record and requests exactly `bytes=start-end`. That is **~0.5 MB instead of the ~13.5 MB file (≈ 25× less)**. Every ranged reply is validated (`206`, `Content-Range`, length, `GRIB…7777` framing) and cached on disk atomically so re-runs are free.
4. **Decode in memory** (`eccodes`, no temp files), roll longitudes 0…360 → −180…180, flip to south→north, convert Pa → hPa, cut to the configured domain (+ padding).
5. **Per-system grids** – for each system and hour: ensemble mean (`nanmean`) with every member's low centers, and the member-wise minimum (`nanmin`) with the member that supplies it at each cell. These are written as **gzip'd binary grids** (`data/<run>/<system>/<mean|min>/fNNN.bin.gz`, ~40 KB each) plus `manifest.json` (schema 4: run info, systems and member lists, class edges, ColorBrewer colours, frames). Nothing else is pre-built. (Wind and gust add `<system>/<wmean|wmax|wprob|gmean|gmax|gprob>/fNNN.bin.gz`, see *10 m wind and gust*.)

### Browser-side processing (and the 1 GB Pages limit)
The pipeline only ships those per-system grids; **the browser does the rest** (`site/engine.js`): it inflates and decodes the grids, forms **any blend** of two or more systems (regridding GEPS 0.5° to the first system's grid), accumulates the **swath**, finds the low centers of every derived minimum field (a port of `detect_lows`, verified identical by the tests), smooths the field (Catmull-Rom) and colours it pixel by pixel on a canvas, and builds the tooltips.

Performance notes: the first frame's grids are requested in parallel with the basemap files; decoded grids are cached by size (oldest first), a probability file is decoded for the one pressure level on screen, finished views are kept in a size-bounded LRU so looping replays without recomputing, rapid scrubbing is coalesced to the latest hour, and the URL hash is written at most about once per second (Safari throws after 100 `replaceState` calls per 30 s).
* **Format** (`gefs_pipeline/gridio.py`): Int16 tenths of hPa, each value predicted from its neighbours (left + up − up-left), residuals zig-zag coded and split into byte planes, then gzip. Lossless to 0.1 hPa; a ~113 k-cell field becomes ~30–40 KB. The basemap is shipped as `*.json.gz` as well; only `manifest.json` stays plain (small, and the workflow reads it).
* **Why `.gz` files rather than relying on Pages' own compression:** the Pages limit (1 GB) applies to the *tar of the site* that is deployed (GitHub's Pages-artifact docs recommend keeping that tar under 1 GB), so JSON counts at its full size, and Pages cannot send `Content-Encoding: gzip` for pre-compressed files. Storing the data already gzip'd makes the stored bytes the compressed bytes, and the browser inflates them itself with `DecompressionStream` (Chrome/Edge 80+, Firefox 113+, Safari 16.4+). A server that has already decoded the file is handled too.
* **Result:** the published site is ~18 MB per cycle (it was ~700 MB with pre-contoured GeoJSON for every blend), every blend combination and the swath cost nothing, and there is no site-size budget to manage. Downloads are small too: a view loads ~40–80 KB per system per hour; the swath fetches the *min* grids of all earlier hours once (~40 KB × hours × systems).
* Because the data are plain numbers in the browser, adding a system or product later needs only the encoder to write another grid and a few lines in `app.js`.

### ECMWF IFS ENS data
Open data from `s3://ecmwf-forecasts` (`<date>/<cycle>z/ifs/0p25/`): the **`enfo`** stream holds the **50 perturbed members**, the control forecast is the deterministic **`oper`** run (the ENS control is identical to HRES since IFS 50r1; older cycles fall back to `enfo` `cf`). Each step has a JSON-lines `.index`; the client reads it once per step and then downloads only the `msl` message of each member by byte range (≈ 0.5 MB each instead of whole multi-GB files). 00/12Z runs have 3-hourly steps to 144 h then 6-hourly to 360 h (the 10-day window uses F000–F240); 06/18Z runs stop at F144. ECMWF GRIB2 uses CCSDS packing (needs ecCodes ≥ 2.2x with AEC support – the pip wheel has it) and its longitudes start at 180°E; the decoder builds longitudes from the grid increments and rolls them to −180…180.

### Canadian GEPS data
Environment and Climate Change Canada's Global Ensemble Prediction System, from the MSC Datamart: `https://dd.weather.gc.ca/<YYYYMMDD>/WXO-DD/ensemble/geps/grib2/raw/<HH>/<hhh>/CMC_geps-raw_PRMSL_MSL_0_latlon0p5x0p5_<YYYYMMDDHH>_P<hhh>_allmbrs.grib2`. 21 members (control + 20), **0.5°** (the only resolution published for the raw members), 00/12Z runs to 384 h (3-hourly to 192 h, then 6-hourly). Unlike the other two, **one file per forecast hour holds every member** (~2.2 MB), so each step is downloaded once and split into members (control first, then by the GRIB `perturbationNumber`; if the keys are missing the file order is used). The Datamart keeps only a few recent days, so very old cycles cannot be rebuilt. GEPS files are posted ~5 h after cycle time. The 0.5° field is contoured after cubic-spline upsampling and, inside a blend, bilinearly regridded onto the finer family's grid.

*Disable a system* by removing it from `[run] families` (e.g. `["gefs", "ifs"]`); the viewer adapts to whatever the manifest contains. If a system fails for an hour (e.g. fewer than 80 % of its members arrive) that hour is built without it, and the viewer simply omits it there.

### ECMWF AIFS ENS data
ECMWF's AI-based ensemble (the Artificial Intelligence Forecasting System, ensemble version), open data in the same bucket as IFS ENS: `https://ecmwf-forecasts.s3.eu-central-1.amazonaws.com/<YYYYMMDD>/<HH>z/aifs-ens/0p25/enfo/<YYYYMMDD><HH>0000-<step>h-enfo-{cf|pf}.grib2` plus a JSON-lines `.index` inventory beside each file. 51 members: the control is in the `-cf` file (`ac00`), the 50 perturbed members in the `-pf` file (`ap01`…`ap50`), 0.25°, **6-hourly to 360 h on all four cycles** (only 00/12Z are used, like the others). The fields used are `msl`, `10u` and `10v`; AIFS ENS has no gust output, so gust is *estimated* from the wind speed like GEPS and AIGEFS.

* **Many small ranges from huge files.** A perturbed-member file is ~2.9 GB, so only byte ranges are practical. A member's `msl`, `10u` and `10v` messages are tens of MB apart, so each member-step costs three range requests (no merging) plus the single-flight `.index` reads. They go through the **same ECMWF limiter as IFS ENS** (`[ifs] requests_per_second`), which is why adding AIFS ENS lengthens a full build to roughly 80–90 minutes. To shorten it: lower `[wind] max_fh`, drop `aifs` from `[run] families`, or raise `[ifs] requests_per_second` (the limiter is adaptive and backs off by itself on 503 *SlowDown*).
* **Optional system.** Like AIGEFS it never holds a cycle back (`[run] optional`); it is included when every step is published, and a later arrival triggers a rebuild of that cycle.
* **Not independent of IFS ENS.** AIFS ENS member *n* is initialised from the same perturbed analysis as IFS ENS member *n*, so a blend of the two is not a blend of independent ensembles (the Help dialog says so). The control also carries model perturbations. Configuration: `[aifs]` in `config.toml` (`model`, `resolution`, `n_perturbed`, `param`, `max_fh`), `[wind.aifs]` (`u`, `v`), and `[wind.estimate] families`.

### NOAA AIGEFS data
NOAA's AI-based ensemble (a GraphCast model fine-tuned on GDAS, run from GEFS initial conditions), on AWS Open Data: `https://noaa-nws-graphcastgfs-pds.s3.amazonaws.com/EAGLE_ensemble/aigefs.<YYYYMMDD>/<HH>/mem<NNN>/model/atmos/grib2/aigefs.t<HH>z.sfc.f<FFF>.grib2` plus a `.idx` file. 31 members (`mem000`…`mem030`; shown as `ai00`…`ai30`), 0.25°, 6-hourly to 384 h, all four cycles (only 00/12Z are used, like the others). Each member file holds many surface fields; the pipeline reads the `.idx` and fetches only the `PRMSL:mean sea level` message (~1.3 MB) with an HTTP byte range, exactly as for GEFS. The data are CC0.
* **Optional systems.** AIFS ENS and AIGEFS never hold a cycle back. AIGEFS is published irregularly (from about 7.5 hours to more than a day after cycle time), so it does not gate the cycle (`[run] optional = ["aifs", "aigefs"]`). A build includes it only when every member is complete for the cycle. If it appears later, the next scheduled attempt sees that the live site lacks it and rebuilds the same cycle with it.
* **Not independent of GEFS.** AIGEFS starts from GEFS initial conditions, so a blend containing both is not a blend of independent ensembles; the Help dialog says so. `mem000` is treated as member 0 (NOAA does not label it as a control in the file metadata).

### Blends (any combination of the systems)
In the viewer choose *Blend* and tick the systems to include; every combination of two or more is available and is computed in the browser.
* **Blended ensemble mean** – by default the **equal-weight average of the system means** (`[blend] weighting = "equal"`), so each system counts once regardless of member count. `"members"` instead averages all members pooled (a 51-member ensemble then outweighs a 21-member one).
* **Blended member minimum** – the lowest MSLP over **all members of the chosen systems** at each grid point; each low center of that envelope is credited to the member that supplies the minimum.
* **Blend lows** – every low center of every member of the chosen systems, drawn in a colour per system (red GEFS, yellow IFS, blue AIFS, teal GEPS, violet AIGEFS; toggle: *View ▸ Colour blend lows by system*).
* **Cursor read-out** – the blended value together with each system's own value and, for two systems, their difference (for three or more: the spread max − min).
* A blend frame exists for an hour only when every system in it has that hour (on a 06/18Z cycle, to F144). Systems are combined on the first listed system's grid; when grids differ (GEPS 0.5° vs 0.25°) the coarser one is interpolated, and the status bar says so.

### Low-pressure centers
For every member, MSLP is lightly Gaussian-smoothed (0.5°) *only to locate* minima; a point is a low when it is the minimum within a 2° radius, below 1005 hPa (as in the reference GEFS image), at least 1.5° from a deeper low, and not on the data border. The *reported* pressure is the raw grid minimum. All of this is in `[lows]` in `config.toml`.

**Member-minimum product:** the same detector runs on the member-wise minimum field (`[lows_min]`, wider 3° radius because the envelope is broad). Each L is attributed to the member that supplies the minimum at that grid cell.

**Swath product:** the same detector runs on the accumulated minimum (or, with the *Swath of* switch on *Ensemble mean* / key **M**, on the running extreme of the ensemble mean itself; a blend folds the *blended* mean hour by hour, computed in the browser from the `mean` / `wmean` / `gmean` grids, so it needs no extra files); each L also carries the forecast hour at which that minimum was reached.

**Cursor read-out:** the browser reads the full-resolution grids directly (bilinear), so a popup follows the pointer anywhere on the map for every product, showing the pressure, a colour swatch, each system's own value in a blend, lat/lon and any low-center markers under the cursor (tap on touch screens). For the swath it also gives the hour the minimum was reached.

### Probability, strike probability and member tracks

**Probability** (key `4`): the share of members whose MSLP is **below a chosen level** at the hour shown. The pipeline writes one extra small file per system and hour (`<system>/prob/fNNN.bin.gz`, a count of members below each level in `[prob] levels`, default 925/950/965/975/990/1000/1005/1010 hPa, coded like the other grids: ≈ 30 kB). The browser turns the counts into percent; a blend shows the equal-weight mean of the systems' fractions (or the pooled share when the blend is set to pooled members), and the tooltip lists each system's own value. The level chips carry the intensity band they belong to (`975 Cat 2+` …). The first class (< 5 %) is left transparent.

**Member low tracks** (`K`, View ▸ Member low tracks): `gefs_pipeline/tracks.py` links every member's detected low centers from hour to hour (predicted position = last position + last motion; a low may not move farther than `[tracks] max_speed_kmh`; tracks shorter than `min_points` are dropped) and writes `<system>/tracks.json.gz` (about 15-50 kB per system). Solid line = the track up to the hour shown, dashed = still to come, one colour per system in blends. Hover a track to highlight it and read the member, its hours and its deepest pressure. Tracks are **only as complete as the low detector** (lows below 1005 hPa, see above), so a track begins when the low first deepens below that threshold.

**Strike probability** (`5`): the share of members with a low **deeper than a chosen level passing within a radius** (`[strike] radii_km`, default 200 km; NHC uses 120 n mi) at any time **up to** the hour shown, i.e. cumulative like the swath. Computed in the browser from the member tracks (`engine.js`: `strikeCounts`): each track is sampled hourly with its pressure interpolated, and every grid cell within the radius of a sample deeper than the level is marked once per member. It is an indicative product built from detected lows, not a verified strike-probability forecast.

**Animated GIF** (File ▸ Export animated GIF…, or the toolbar button): choose the first and last hour, size and speed; the browser steps through the frames, composes the map layers exactly as shown (theme, opacity, overlays, tracks and, optionally, the colour legend) and encodes the GIF itself (`site/gif.js`). **Crisp:** colours are exact 24-bit values, never reduced to 15 bits and never dithered, so flat map colours, class colours and the legend come out pixel for pixel (when an animation has <= 255 colours the whole file is exact; otherwise one global palette is built by weighted median cut + k-means, a colour that dominates its entry is kept exactly, and every pixel takes its nearest palette colour, so only the anti-aliasing blends of text and lines are approximated). *Size* goes up to the screen's real pixels (CSS pixels × device pixel ratio, at most 1600 wide); the default is the largest size up to 1000 px wide and 0.7 megapixels. **Small:** one global palette, only the changed box of each frame stored with unchanged pixels transparent (or, when it makes a longer run, in their own colour), identical frames merged into one longer delay, LZW. In tests this is smaller than ImageMagick's `-layers OptimizePlus`. *Max file size* (default 8 MB) is a safety net: if the exact file is larger, the encoder reduces detail in small steps (fewer palette colours, changes below a small tolerance ignored) until it fits, and says so when it is still over at the lowest step. **Every frame carries the title and subtitle** (system, product title, units, init time, forecast hour, valid time, member count), drawn at a fixed layout that does not depend on the screen size, and the file name and the GIF comment field describe it (`ensemble-<mslp|wind|gust>_<system>_<product>[_<level><hPa|mph>][_<radius>km]_<run>_F000-F240.gif`). To keep it fast, layers that do not change between frames (land, lakes, borders, graticule, legend) are flattened once, the grids of the next frames download while the current one is drawn, and nothing waits for a repaint. Measured on a synthetic test storm in headless Chrome, a 41-frame (F000-F240) export at 1000 px with exact colours takes about 3 s and 0.5 MB (pressure), 1.2 MB (wind) or 1.4 MB (gust); nothing is uploaded anywhere.

### 10 m wind and gust (mph)

The *Field* switch (**P**ressure / **W**ind / **U** = gust) shows 10 m **sustained wind speed** and **wind gust** in mph with the same four products as pressure – no extra tools needed for the usual Nor'easter questions: *how strong is the wind at the coast (mean), what could any member produce (highest member), how strong does it get over the whole event (swath), and how many members reach advisory / warning / gale / storm / hurricane-force winds (probability)*. Strike probability and the L markers are pressure-only; the member low tracks (**K**) can be shown over any field.

| System | Wind speed | Gust | How |
|---|---|---|---|
| NOAA GEFS | ✓ | ✓ | `UGRD` + `VGRD` at 10 m (speed computed from the components, one byte-range request because the two records are adjacent) and `GUST` at the surface (instantaneous) |
| ECMWF IFS ENS | ✓ | ✓ | `10u` + `10v`; gust `10fg3` (max over the previous 3 h) / `10fg` (previous 1 h on early steps), **absent at F000** |
| CMC GEPS | ✓ | est. | `WIND_TGL_10` (speed, one file per hour for all members); gust **estimated** from the wind (see below) |
| NOAA AIGEFS | ✓ | est. | `UGRD` + `VGRD` at 10 m from the same `.idx` byte-range request as the pressure; gust **estimated** from the wind |

* **Products.** Per system and hour the pipeline writes the ensemble mean (`wmean` / `gmean`), the highest member with its owner (`wmax` / `gmax`) and a member count at or above each threshold (`wprob` / `gprob`), in half-mph steps (header `scale` = 2; Int16 with the same predictor + byte-plane coding, ~40 kB each). The **swath** (the running maximum, with the hour and member that set it) and every **blend** are computed in the browser from those grids, exactly like the pressure swath and blends; for a blend the highest member is the highest over all chosen systems.
* **Colours.** Wind speed and gust each follow a supplied legend, class for class and colour for colour (hex values sampled from the legend images; `[wind_scale]` and `[gust_scale]` in `config.toml` list the edges and colours outright). **Wind speed:** 5-10, 10-15 … 45-50, 50-60, 60-70 mph, dark blue → teal → green → yellow → orange; below 5 mph is transparent and 60 mph and above keeps the top colour. **Gust:** 0-5 (dark navy), 5-10 … 45-50, 50-60, 60-70, 70-80, 80-100, 100-120, 120-140, 140-150 mph, blue → green → yellow → orange → red → dark red → pink → magenta; 140 mph and above keeps the top colour. The two fields therefore no longer share one scale: the same colour means a different speed on Wind and on Gust, so read the legend. The legend bar numbers every class edge (every second one on a narrow phone screen) and no longer names NWS bands under the bar; the cursor read-out still says "≈ Wind Advisory range", "gale-force / High Wind" etc. from the real thresholds (25, 40, 55, 75 mph, `[[wind_scale.categories]]`). Probability uses its own yellow-orange-brown scale (first class < 5 % transparent). Thresholds, names and colours are in `[wind]`, `[wind_scale]`, `[gust_scale]` and `[products.wmean … gprob]`.
* **Estimated gust (AIFS, GEPS, AIGEFS).** These three systems publish no gust, so the pipeline estimates one from each member's wind speed: `gust = wind × factor(wind speed, land or water)` (`gefs_pipeline/gustest.py`; land / water from the basemap polygons, `gefs_pipeline/landmask.py`). Over land the factor is about 2.0 at light winds, falling to ~1.6 at 25 mph and ~1.4 at 40 mph; over water it is ~1.26–1.3. The curves are the average of what GEFS and ECMWF forecast for the same wind speeds (120 member-fields each; `[wind.estimate]` in `config.toml`, re-fit with `python tools/calibrate_gust.py --cycle YYYYMMDDHH`). It is applied to **each member before** the ensemble statistics, so the highest member and the exceedance probabilities remain meaningful, and it is labelled **"est."** everywhere (system chips, title, legend note, pop-up, GIF text and comment). In the viewer the estimated systems are opt-in: switching to *Gust* keeps the systems with a real gust forecast and the blend chips add GEPS / AIGEFS back. How good is it? Against the real gusts of GEFS and ECMWF it is unbiased over land (−0.1 mph for winds ≥ 10 mph) and, over water, sits between the two models (+2.5 mph vs GEFS, −2.6 mph vs ECMWF, correlation 0.95) because the two disagree about water gusts (GEFS ≈ 1.1–1.2 × the wind, ECMWF's 3-hour maximum ≈ 1.4 ×). **Weak spot: over land** a single factor cannot reproduce gusts that come from terrain, mixing and convection (correlation ≈ 0.65): in the calibration sample the estimate produced 2.5–3 × fewer cells with gusts ≥ 35 mph and far fewer ≥ 46 mph than the models' own gusts, so over land treat it as a **lower bound**; the sample was one quiet-ish cycle and land winds above ~27 mph did not occur in it (that part of the curve is a physical taper, not a fit). Over water – the coastal-storm use – it is the better case. Set `[wind.estimate] enabled = false` to switch it off.
* **Calm cells are skipped in the browser.** Winds and probabilities start with a transparent class, so most of a map is calm (measured on a real cycle: 87 % of cells below 25 mph; 88–100 % of cells at 0 % in the probability planes). `rasterize()` skips a pixel whose four surrounding grid values are all below the first colour (a bilinear mix cannot reach it), which draws a wind map about 3× faster (1280×560 px: 11.5 → 3.5 ms) with identical pixels (tested, including values hugging the class edges, NaNs and three colour tables). A cell of *exactly* 0 mph is practically absent from 10 m wind (0.00–0.02 %), so a literal "skip zeros" would save nothing there; the other browser steps – regridding (all four systems share one grid, so none happens), blending (~1.5 ms), the highest-member fold (~1 ms) – cost only milliseconds and were left as they are.
* **Limits to keep in mind.** These are *model* 10 m winds on a 0.25° (GEPS 0.5°) grid: terrain, shorelines, bays, urban effects and convective gusts are not resolved, and ensembles of 21–51 members under-sample the extremes, so use the highest-member and swath products as an upper envelope, not a forecast of the peak. The **mean of a gust** is much smoother than the gusts any member shows – prefer *highest member*, *swath* and *probability* for damaging-wind risk. ECMWF's gust is a 1–3 h maximum while GEFS's is instantaneous, so gusts from the two are not exactly alike; GEPS and AIGEFS have no gust of their own and show an *estimated* one (see above). The ECMWF gust and every blend including it start at F006.
* **Cost.** Wind and gust roughly triple the number of requests and the data downloaded per build (each member needs its own byte ranges: GEFS three requests – MSLP, `UGRD`+`VGRD`, gust – plus its `.idx`, ECMWF IFS four – MSLP, `10u`, `10v` and the gust are tens of MB apart in the file –, AIFS ENS three (no gust), AIGEFS one range for MSLP and wind together plus its `.idx`; GEPS adds one extra file per hour); the workflow's job timeout was raised from 90 to 180 minutes accordingly and add roughly 0.1–0.15 MB of site per system, field and hour (the published site grows from ~18 MB to about 50–60 MB per cycle, still far below the 1 GB limit; a view downloads ~40–60 kB per system and hour, plus the swath's earlier hours). Knobs: `[wind] families` (which systems), `max_fh` (stop earlier, e.g. 120 for the first five days), `enabled = false`, or `--no-wind` on the command line. The viewer needs no change: with no wind data in the manifest, the *Field* switch is simply not shown.

### Rate-limit / server-friendliness
* **One request limiter and one worker pool per host**, each with its own ceiling: GEFS `[source] requests_per_second = 10`, ECMWF `[ifs] = 3` (shared by IFS ENS and AIFS ENS – same bucket –; it answers 503 *SlowDown* above ~4–5/s), GEPS `[geps] = 4`, AIGEFS `[aigefs] = 8`; any other host uses `[fetch] requests_per_second = 8`. `[fetch] workers = 6` keep-alive connections *per host*. A single shared pool would let the slowest host's waiting workers starve the others (a frame took the *sum* of the systems' times); per-host pools make it the *longest*. Measured on the same small live build (GEFS + ECMWF + AIGEFS, 6 members, 3 frames): 37 s → 27 s.
* **Mirrors for ECMWF.** The ECMWF open data on AWS is shared by thousands of users and often answers `503 SlowDown` however gently it is asked (ECMWF's forum documents this, and recommends the mirrors). `[ifs] mirrors` therefore lists a second server holding the same files (Google Cloud, `storage.googleapis.com/ecmwf-open-data`; `[]` turns it off). Requests rotate over AWS and the mirrors; a server that answers 503 / 429 / 5xx or drops the connection is put on a cool-down (30 s, doubling to 10 min while it keeps failing) and the retry goes to another server at once instead of sleeping; a server that answers 404 (its copy may lag behind) is skipped for that request only. Each server has its own adaptive limiter (`[ifs] requests_per_second` for AWS, `mirror_requests_per_second` for each mirror) and its own line in the end-of-build log, which also reports the number of fail-overs. ECMWF's own server (`[ifs] last_resort`, `data.ecmwf.int`, limited to 500 simultaneous connections for the whole world and often slow) is the **last resort**: it is used only while AWS and every mirror are cooling down, at its own gentle `last_resort_requests_per_second`. A server that answers with something unusable (for instance a `200` for a Range request, which would mean downloading a whole 2.9 GB file) is abandoned the same way, without reading the body. Microsoft's Azure copy needs a signed token and is not used.
* **Time budget – a slow system never holds the build hostage** (`[budget]` in `config.toml`, `0` turns a rule off). (1) A system that has not delivered an hour's members within `frame_timeout_minutes` (12) is skipped for that hour: members that did arrive are used when they are at least `min_member_fraction` of the system, the rest of that hour's downloads are abandoned at their next request (no hanging threads) and the next hour starts. (2) `strikes` (2) such hours in a row drop the system for the rest of the build. (3) `family_minutes` (110): a system whose own downloading has taken that long in total is dropped; waiting for a slower system does not count, so a system that keeps up is never penalised. (4) `build_minutes` (150): everything stops and the hours built so far are published, so the forecast simply ends earlier. A dropped system keeps its hours so far and the other systems carry on to the end; a system that delivered nothing at all is not offered. The viewer says so in the title bar (“⚠ AIFS ends at F096 (data download too slow)”, details on hover) and the manifest carries `incomplete`. The build log lists every strike, drop and the final `SUMMARY` lines.
* **Adaptive:** a `429` / `503` halves that host's rate (at most once every 2 s, never below 20 % of the ceiling) and it climbs back 15 % per 25 clean replies up to the ceiling, so a throttling server is eased off instead of hammered; the end-of-build log prints one line per host (requests, byte-range vs whole-file, MB, kB per read, retries).
* Exponential backoff **with jitter** (1, 2, 4 … ≤ 60 s) on `429`, `5xx` (S3 *SlowDown* = 503) and network errors; honours `Retry-After`; 404 is never retried; hard stop after `max_retries`.
* **Byte ranges, as few requests as possible.** Requests, not bytes, are what the servers' limits count, so every download is a `Range` request for exactly the wanted GRIB message(s) (S3 takes one range per request; the `.idx` / `.index` inventory says where, read once per file and shared by the pressure and wind fields – single-flight, so two workers never fetch the same inventory). Wanted messages that are adjacent, or less than `[fetch] merge_gap_kb = 1024` kB apart, share one request: GEFS `UGRD`+`VGRD`; AIGEFS `UGRD`, `VGRD` and `PRMSL` (≈ 0.6 MB of unwanted temperature in between, but 1 request instead of 3). Messages tens of MB apart (GEFS gust and MSLP, every ECMWF field) stay separate – bridging them would multiply the bytes for one request fewer. `0` turns merging off. Checked against the live servers: every GEFS / AIGEFS / ECMWF read is a `206`, the average read is 0.6–1.8 MB, and no whole file is downloaded except GEPS's (its 21 members share one file, so a whole-file read *is* the minimum).
* Range requests + `.idx` (≈ 25× less data), on-disk cache (a rebuild of the same cycle makes no data request), one-frame look-ahead (next frame downloads while the current one is contoured), explicit `User-Agent` (auto-set to your repo in Actions).
* Members that fail after retries are dropped; a frame is published only if ≥ 80 % of members arrived (`min_member_fraction`).
* The scheduled workflow skips the whole build when the live site already serves the newest cycle.

### Interface

A flat, operational-workstation layout: title bar, **menu bar** (File · View · Ensemble · Products · Help), **toolbar** (ensemble-system switch GEFS / IFS / AIFS / GEPS / AIGEFS / Blend, field switch Pressure / Wind / Gust, product switch, data opacity, GIF, reset view, theme), map with a two-line title block in the standard model-graphic layout (line 1: system | product title, with units at the right; line 2: init time · forecast hour · valid time · member count, all in sentence case), a flat colour bar, a time bar, and a **status bar** showing the cursor's lat/lon, pressure and nearest low. A cursor-following pop-up gives the same read-out on the map; in a blend, tick-boxes on the map choose the systems. In the map's legend-style keys (the blend tick-boxes and the per-system rows of the pop-up) each system is marked by its publisher's flat flag icon (inline SVG) – 🇺🇸 GEFS and AIGEFS, 🇪🇺 IFS and AIFS, 🇨🇦 GEPS.

**Dark / light theme:** View ▸ Theme, the toolbar button, or the **T** key. Dark is the default; the choice is remembered in the browser. Map colours per theme (land, borders, graticule, L markers) live in `THEMES` at the top of `site/app.js`; page chrome colours are CSS variables at the top of `site/style.css`.

## 3. Cartography & colour

* **Basemap**: Natural Earth 1:10m (public domain), clipped to the data domain and simplified at build time. Stacking order, bottom → top: land fill · **data** · lakes · coastline · state/province lines · international boundaries.
* **Line hierarchy** (standard practice – weight and contrast follow administrative rank): international boundaries are the heaviest and darkest, with a light casing so they stay legible over both dark and light fills; disputed/indefinite boundaries are dashed; treaty/median maritime lines are fine grey dots; first-order divisions (states, provinces) are thinner mid-grey with a faint casing; coastlines are finest. **All widths scale ≈ 20 % per zoom level.** Lakes are drawn as water cut-outs above the data. The lat/lon graticule is a thin dotted vector layer drawn *beneath* the coast/state/country lines (only its degree labels sit on top), with density adapting to zoom (10° → 1°). State/province lines use every Natural Earth admin-1 class (including "statistical" and "meta bounds" classes, which are real state borders for the US and Canada), so no border segments are dropped.
* **Colour** – one shared 5 hPa-class scale for all products (edges, ramps and labels are in `config.toml` → `[scale]`). The class edges sit exactly on standard storm-intensity thresholds, so a colour change *is* a threshold crossing:

  | Pressure (hPa) | Band | Wind it stands for | Ramp |
  |---|---|---|---|
  | < 925 | Cat 5 | ≥ 137 kt | RdPu (darkest purple) |
  | 925–949 | Cat 4 | 113–136 kt | RdPu |
  | 950–964 | Cat 3 | 96–112 kt | RdPu |
  | 965–974 | Cat 2 | 83–95 kt | RdPu |
  | 975–989 | Cat 1 / hurricane-force | 64–82 kt | RdPu (pink) |
  | 990–999 | Storm force | 48–63 kt | Blues (navy) |
  | 1000–1004 | Gale force | 34–47 kt | Blues |
  | ≥ 1005 | below gale | < 34 kt | RdYlBu (diverging; pale yellow ≈ 1015–1020, red ≥ 1030) |

  The wind thresholds are the NWS marine-warning categories (gale 34–47 kt, storm 48–63 kt, hurricane-force ≥ 64 kt) and the Saffir-Simpson hurricane wind scale. They are translated to pressure with NOAA's Dvorak current-intensity table (Atlantic), linearly interpolated and rounded to 5 hPa (a unit test reproduces the edges from the table). **Treat it as a guide, not a classification:** pressure does not fix wind speed (gradient, storm size and latitude matter, and the NW Pacific table is ~10 hPa lower), so a 985 hPa nor'easter is not a Cat 1 hurricane and extratropical gales happen at higher pressures; model MSLP at 0.25° also under-represents the deepest tropical-cyclone pressures. The legend names the bands under the bar and the cursor read-out says "≈ gale-force pressure" etc. Colours are interpolated in OKLab between ColorBrewer anchors.
* **Low markers** – a bold red **L** (ColorBrewer Reds) with a white halo and the member's central pressure in hPa directly above it. Markers and labels are large and grow with zoom; labels are de-cluttered (deepest lows labelled first; more appear as you zoom in). The cursor read-out lists every low under the pointer with its member and exact value. Both products show L + hPa.
  Change `edges` and the `[[scale.segments]]` in `config.toml`; available ramps are listed in `gefs_pipeline/palette.py`.
* Web-Mercator projection (the web-map standard). The projection of your reference images is not reproduced.

## 4. Publish on GitHub Pages (exact steps)

### One-time
1. **Create an empty repository** on GitHub (e.g. `gefs-mslp-viewer`) – *no* README, `.gitignore` or licence (the project already has them).
2. In that repo: **Settings → Pages → Build and deployment → Source: “GitHub Actions”.**
3. In your terminal, from the unzipped project folder:

```bash
cd gefs-mslp-viewer
git init -b main
git config user.name  "Your Name"            # only if not already set globally
git config user.email "you@example.com"
git add .
git status                                   # sanity check: no dist/, .cache/ or .venv/ listed
git commit -m "Initial commit: GEFS MSLP pipeline and Pages viewer"
git remote add origin https://github.com/<YOUR-USER>/<YOUR-REPO>.git
git push -u origin main
```

Using the GitHub CLI instead (does steps 1–3 in one go; Pages must still be set to “GitHub Actions” in Settings, or run
`gh api -X POST repos/<YOUR-USER>/<YOUR-REPO>/pages -f build_type=workflow`):

```bash
git init -b main && git add . && git commit -m "Initial commit: GEFS MSLP pipeline and Pages viewer"
gh repo create <YOUR-REPO> --public --source=. --remote=origin --push
```

4. The push starts the workflow. Watch **Actions → “Build & deploy Ensemble Blender Tool”**. The first full build takes roughly 10–20 min. If you pushed *before* enabling Pages, the `deploy` job fails – enable Pages, then **Actions → the failed run → Re-run failed jobs**.
5. Your viewer is at **`https://<YOUR-USER>.github.io/<YOUR-REPO>/`**.

### Afterwards
* Runs automatically at 08:35, 09:35, 10:35, 11:35 and 20:35, 21:35, 22:35, 23:35 UTC (ECMWF open data for the 00Z/12Z runs completes ≈ 7.5–9 h after cycle time; GEFS and GEPS are done earlier; AIFS ENS arrives with or a little after IFS ENS; AIGEFS is the most irregular). A run whose cycle is already live *with every system that is ready now* is skipped; a late AIFS or AIGEFS therefore triggers a rebuild of that cycle. Edit the `cron` line to change. A build downloads ≈ 15 GB with wind, which fits comfortably in the hosted runner's time and disk limits.
* **Run it by hand:** Actions → *Build & deploy* → *Run workflow* (options: pin a `cycle`, limit `max_fh`, `force`).
* Change `config.toml` (domain, hours, palettes…) and push – the site rebuilds.
* GitHub disables scheduled workflows after 60 days without repository activity (public repos) – push any commit or re-enable them in the Actions tab.
* Custom domain? Add a repository *variable* `SITE_URL` (Settings → Secrets and variables → Actions → Variables) so the “already deployed?” check looks at the right address.
* GitHub Pages on a *private* repository needs a paid GitHub plan; public repos are free.
* Pages keeps **only the latest cycle** (each deploy replaces the site). Archive older cycles if you need them.
